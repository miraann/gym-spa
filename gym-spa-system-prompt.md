## Core concept
Every member gets an **NFC card** (MIFARE / NTAG). At the entrance, staff or a kiosk scans the card → the system identifies the member, checks the active plan, applies the rules, records the visit, and shows a clear result screen (green = allowed, red = denied with reason, yellow = warning such as "expires in 3 days").

## 1. NFC integration
Support every platform behind one `NfcReader` interface (in `/packages/platform/nfc`):
1. **USB desktop reader (Windows EXE + web)** — any reader in keyboard-wedge (HID) mode that types the card UID + Enter. Build a focused, always-listening input on the check-in screen that captures fast keystroke bursts (< 50 ms between chars) and ignores normal typing. **PC/SC readers such as the ACR122U** (they don't type) are read by the Windows EXE directly: required, step 2f (below).
2. **Android (APK)** — native NFC through a Capacitor NFC plugin (read tag UID in foreground). Android tablets can be used as a check-in kiosk.
3. **iOS (later phase)** — choose a Capacitor NFC plugin that also supports Core NFC, so iOS works later without rewriting.
4. **Web NFC API** — fallback for Android Chrome when running as a PWA (`NDEFReader`). Feature-detect and fall back to manual search.

Rules:
- Store the card UID **normalized** (uppercase hex, no separators) in `nfc_cards.uid` with a unique index.
- A member can have multiple cards over time, but only **one active** card. Support: assign, replace (lost/damaged, with optional fee), deactivate, blacklist.
- **Decided by the user on 2026-10-19 (Phase 2 plan), built in steps 2d–2f:**
  - A card UID is unique **per gym**, not across the whole system: two gyms' cheap 4-byte cards can share a UID, and a system-wide check would tell one gym that another has that card.
  - The design accepts 4-byte and 7-byte UIDs, and readers that type a 10-digit decimal number (e.g. 125 kHz EM readers).
  - **Lost or damaged:** the old card stops working at once; the new card can be given in the same step. A lost card that turns up can be given out again.
  - **Stolen:** the card is also blocked (`cards.blacklist`). Nobody can be given it until a manager unblocks it, and the check-in screen (Phase 4) shows that it was reported stolen. A receptionist marks a card lost, which already stops it; a manager blocks it if needed.
  - **Returned** (the member leaves): the card can be given to someone else. Archiving a member returns their card.
  - The replacement fee comes with Phase 3 (payments). A read-only gym can't change cards.
  - **UIDs as readers give them** (step 2d): hex with or without separators, or exactly 10 digits (a 4-byte number), in the card's byte order or reversed (some keyboard-type readers); always stored as uppercase hex of 4, 7 or 10 bytes. The app (`normalizeCardUid()`) and the database (`app.normalize_card_uid()`) run one shared list of test cases.
- **Card hardware (decision 6, answered by the user on 2026-10-19):**
  - **Reader:** the user's desk reader is an ACR122U-type USB reader. It is PC/SC, not keyboard-type, so **ACR122U support in the Windows EXE is part of Phase 2**, its own step 2f after 2e: a maintained PC/SC native module in Electron's main process (licence and the Electron rebuild checked first), exposed to the page over IPC as UID events only, behind the same `NfcReader` interface. It reads the UID with the standard Get UID command (`FF CA 00 00 00`), handles the reader being plugged in and out, and uses the reader's beep and LED for success and error where it can.
  - **A card already lying on the reader (decided by the user on 2026-10-22, step 2f):** after the app starts, the PC wakes from sleep, the reader is plugged in again or the smart card service recovers, a card that is already on the reader is **not** a new scan; staff lift it and place it again. When staff open a card screen themselves (give or replace a card, the reader test in Settings) and a card is already on the reader, it is read once, because that is an intentional action. **Phase 4 check-in counts only a newly placed card**, so a card left on the reader never checks anyone in by itself.
  - **Decided by the user with the 2f plan (built in step 2h):** "a card scanned on any screen opens that member" works the same for the PC/SC reader as for the keyboard-type reader, and follows the rule for a card already lying on the reader above.
  - **Keyboard-type readers** stay supported as planned: other gyms may have those.
  - **The web app can't use PC/SC:** it shows a clear message that reading cards at the desk needs the Windows app, a keyboard-type reader, or an NFC phone.
  - **Cards:** the user's test cards are NXP NTAG215 type (ISO 14443-3A, NFC Forum Type 2, 7-byte UID, no password). Their NXP originality signature is invalid, so they are compatible clones. **The UID is the card's identity** (uppercase hex); 4-byte UIDs are still accepted. The NXP signature is never relied on.
  - **README (NFC section):** recommend genuine NXP NTAG213/215 cards for real gyms (signature "Valid" in NFC Tools). Clones work, but their UID may be changeable, so a card can be copied.
  - **Phase 4:** the check-in screen shows the member's photo on every scan, so staff can spot a copied card.
  - **Later (iOS):** the user tests with an iPhone, so the future iOS app reads cards through Core NFC. No change to Phase 2.
- Never trust the UID alone for sensitive actions (payments, refunds) — require staff login.
- Manual fallback: search member by name/phone/member code if the card is forgotten (log it as `method = 'manual'`).

## 2. Check-in engine (most important part)
Implement as one Postgres function `check_in(card_uid, branch_id, method, device_id)`, called with `rpc()` and running in a single transaction (result in < 300 ms). It checks the rules and inserts the attendance row together, so two devices scanning at once can't both use the last visit. It returns a typed result object (parsed with Zod in the app). The staff member comes from the session (`auth.uid()`), never from the request.

**Important:** do NOT store "remaining visits" as a counter that gets decremented. Store attendance as append-only rows and compute `remaining_visits = plan_visits + adjustments - count(valid attendance)`.

Logic order:
1. Card exists, is active, not blacklisted → else deny `CARD_INVALID`
2. Member status is active (not suspended / banned) → else deny
3. Find the active subscription valid for this branch and today
4. Subscription frozen? → deny `PLAN_FROZEN`
5. Expired by date? → deny `PLAN_EXPIRED`
6. **Plan type rules:**
   - `time_based` (monthly, 3/6/12 months): allowed while `today <= end_date`
   - `visit_based` (e.g. 12 sessions): allowed if computed `remaining_visits > 0` (the new attendance row reduces it — no counter)
   - `hybrid` (e.g. 20 visits within 2 months): both rules
   - `unlimited` / `vip`
7. **Time window rules:** plan may restrict hours (e.g. morning-only, women-only hours) and days of week
8. **Anti-passback / cooldown:** if the same member checked in within the last N minutes (configurable, default 60), do NOT deduct another visit — return `ALREADY_CHECKED_IN`
9. **Daily limit:** max visits per day per plan (default 1 for visit-based)
10. **Outstanding debt:** if member owes more than a configurable amount → warn or deny (setting)
11. Insert `attendance` row (check-in time, branch, method, staff, plan snapshot)
12. Return: member photo URL, name, plan name, remaining visits / days, expiry date, warnings, assigned locker (if any), unpaid balance, birthday flag

Also implement `check_out(...)` (optional, for occupancy tracking and locker release) and a **live occupancy counter** (per branch, with cross-branch totals for managers).

## 2.5 Two editions & the server (applies to every module)
- **Online edition:** Web/PWA, Android and Windows, against Supabase in the cloud. **Always needs internet.**
- **Offline edition:** **Windows EXE only**, never uses the internet. Several PCs (reception, kiosk, cashier) share one **server PC on the gym's local network**, which runs Postgres + PostgREST + Supabase-compatible Auth as Windows services behind a small `gym-server` proxy. One installer with two modes ("This PC is the server" / "Connect to the server"), a pairing code per PC, encrypted LAN traffic (a certificate the server makes for itself), LAN discovery with a manual address fallback, daily automatic backups + restore, updates by installer on USB (server and PCs must run the same version).
- **One app, one set of migrations:** the app only knows one server address. The same end-to-end tests run against both servers.
- **No local data:** every screen reads and saves through the server under the acting staff member's own session. Without a connection the app shows a clear message (always-visible connection indicator: Connected / No connection / Server not responding, last check time, "Check again") and saves nothing.
- **IDs:** generate UUIDs on the client (never rely on server sequences for primary keys).
- **Invoice / receipt numbers:** given by the server per branch, e.g. `B1-000457`.
- **Multi-row operations** (payment + invoice + items + subscription, locker assignment, spa booking) are one Postgres function each, all-or-nothing.
- **Concurrency rules:**
  - Attendance, payments, stock movements, audit logs: append-only
  - Member profile edits: last write wins, with `updated_at` + `updated_by`
  - Locker assignment and spa room/therapist booking: constraints in Postgres; the second booking of the same slot/locker gets an error at once
  - Visit limits: checked and recorded in one transaction (`check_in`), so no double use
- **PIN switching on shared PCs:** a staff member logs in with their password once per device; others switch to them with a PIN. The server checks the PIN, counts wrong tries and locks it (a password login unlocks it); PIN hashes never leave the server.
- **Devices must be registered** (decided by the user on 2026-10-11, built in step 1e): a staff member with `devices.manage` registers a device once, at their first login on it (a name and its branch); anyone else is refused on an unregistered device and asks a manager. The device then works in that branch, and the PIN works only on a registered, active device of an active branch (`unlock_on_device`). Every registered device counts toward the gym's device limit, an Owner's or manager's personal phone too. Managers rename, move and deactivate devices on the devices screen. The device id comes from the device, so this is a deterrent, not a security boundary: data access is still decided per staff member by RLS.
- **Internet-only features** (online edition only; hidden in the offline edition): SMS/WhatsApp, online payment gateways, cross-branch cloud reports.
- **Member photos are kept in Postgres**, like the gym logo (decided by the user on 2026-10-19, replacing Supabase Storage online and files on the server PC offline): the app resizes a photo to at most 480 px and 150 KB, plus a thumbnail of at most 12 KB, and the database checks the size and the file type again. So both editions work the same, with no storage service on the offline server, and every backup includes the photos. Built in step 2c.
- **Staff accounts** (create, reset password, deactivate/reactivate, change username) use Supabase Auth's official admin API, from **one shared TypeScript module** that runs as an Edge Function in the online edition and as a `gym-server` route in the offline edition. The secret key exists only there. The module first checks the caller's rights in Postgres under the caller's own session, then calls Auth, then writes the staff rows under the caller's session (so the usual guards run). If that last step fails, it removes the new Auth user again (compensation). Decided by the user on 2026-10-10 after the auth spike (`spikes/windows-auth/README.md`). Further decisions with the MT-2 plan (2026-10-10):
  - **Temporary passwords:** for create and password reset, the server generates a random temporary password (at least 12 characters, no look-alike characters such as 0/O and 1/l/I) and returns it once. The manager never types a password. The app shows it once with a copy button and a Kurdish note that it is shown only once. `must_change_password` stays true, so staff set their own at first login. The temporary password is never logged.
  - **Logins left behind** by a failed compensation may be deleted (so their username works again) only if the email has the staff login form (`@<gym code>.staff.gym-spa.invalid`), the user is not a platform admin, it has no staff row, and it is more than 2 minutes old. pgTAP tests prove that a non-staff email and a platform-admin-like user are never picked.
  - **Read-only gym:** deactivating staff and resetting passwords still work (they only take access away); creating, reactivating and renaming are refused. `bootstrap:admin` stays as it is; the seller panel (MT-3) creates a gym's first Owner through this module. Renaming doesn't sign the staff member out.
  - **Token check first (decided with the MT-2 review, 2026-10-10):** the gateway's JWT check is off for the staff function, so the handler itself first verifies the bearer token's signature and expiry against the project's JWKS and requires `role = authenticated`, before any database call and before the secret key is used. A forged, expired or anon token gets 401. The database check stays the real permission check. The offline server's Auth therefore signs with an asymmetric key, so it publishes a JWKS.

## 2.6 Many gyms: tenants, seller panel and licenses
Click Group sells the system to many gyms. The requirements were decided by the user on 2026-10-10, and the multi-tenant plan was approved the same day, with the user's additions (Lock, recovery codes, two platform admins, key safety).

- **Online edition: multi-tenant.** Many gyms share one cloud project. **Offline edition:** the same schema with exactly one gym row, so the code stays identical.
- **Isolation:**
  - A `gyms` table. Every business table has `gym_id`, and RLS checks it on every table. A staff member belongs to exactly one gym, and a row's `gym_id` never changes.
  - Composite foreign keys (for example `(branch_id, gym_id)` → `branches (id, gym_id)`) make a link between two gyms' rows impossible in the database itself, even for server code with the secret key.
  - pgTAP tests prove that gym A can never read or write gym B's data, on every table. The table list comes from the database catalog, so new tables are covered automatically.
  - The `permissions` catalog stays global, because the platform defines it.
- **Gym roles:** the gym's top role is **Owner** (خاوەن, key `owner`). It was called Super Admin before this step; the new name keeps it apart from the platform admins. The built-in roles are copied into each gym when the gym is created, and a gym's custom roles belong to that gym.
- **Login:**
  - Usernames are unique per gym, not globally. The login email is `<username>@<gym code>.staff.gym-spa.invalid`.
  - **The gym code is permanent:** 3 to 20 lowercase Latin letters, digits and `-`, and it can never change, because it is part of every login. Before creating a gym, the seller panel shows a clear Kurdish warning that the code can't be changed later.

  - The first login on a device asks for the **gym code**, username and password. The device then remembers the gym: the login screen shows the gym's name and logo and asks only for username and password. "Use another gym" appears only when no staff member is logged in on the device.
  - On the web, a link like `…/?gym=<code>` fills in the gym code, which also helps when installing the PWA.
  - The offline edition has exactly one gym and never asks for a code.
  - A wrong gym code, username or password gives the same message, so nobody can find out which gyms or usernames exist.
  - The PIN lockout, the settings and the audit log are per gym.
- **Seller panel** for the platform owner (Click Group):
  - **A separate app, `apps/seller`:** web only, with its own Content-Security-Policy. It is never part of the APK, the EXE or the offline edition, and the gym app's bundle contains no seller code. Shared code comes from `packages/`. **Where it is served (changed by the user on 2026-10-11):** for now no separate domain and no DNS: it is deployed together with the gym app, by the same Vercel project, at `https://gym-spa-ten.vercel.app/seller/`. It stays its own app and build (Vite base `/seller/`, its own output folder, which the one Vercel build copies into the gym app's output under `/seller/`). Moving it to its own domain later (for example `seller.clickgroup.site`) is documented in the README.
  - **Platform admins:** `platform_admins` accounts are completely separate from gym roles. One login can never be both a staff member and a platform admin, and a gym's Owner can never reach the panel. Platform admins log in with a real email address.
  - **Two-step login (TOTP) is required.** Every seller function checks that the session passed the second step (`aal2`).
  - **Recovery codes:** setting up TOTP creates one-time recovery codes. They are shown once and stored only as hashes. Using one removes the lost TOTP device, so the admin sets up a new one right away. Every use is logged.
  - **At least two platform admins,** so losing one phone never locks Click Group out. The panel warns while there is only one, and the last active platform admin can't be deactivated. A platform admin can reset another platform admin's two-step login.

  - **What the panel does:** creates a gym with its first Owner account, sets an online gym's subscription dates, suspends, locks or reactivates a gym, and shows usage numbers per gym (counts only, never member data).
  - **Seller audit log:** `platform_audit_logs` records every seller action: who, when, which gym, what, and the reason where one is required.

Each one starts with `app.require_platform_admin()`: an active platform admin whose session passed two-step login (`aal2`) and who chose their own password.     - **How it is built (the MT-4 plan, written by Claude on 2026-10-28 under the working rules; released together):** sub-steps **MT-4a** database and pgTAP, **MT-4b** the gym app's screen and notice, **MT-4c** the seller panel's support screens.

  - Offline gyms follow their license (below).

- **Offline licenses (serial keys):**
  - **The license:** each offline gym gets a unique license, created in the seller panel. It is signed with Ed25519 and contains:
    - the gym id and gym name;
    - the license type (yearly or perpetual), max branches, max devices and edition features;
    - the issue date, plus either an expiry date (yearly) or an "updates until" date (perpetual);
    - the license id, and the id of the key that signed it (`kid`).
  - **Format:** `GSL1.<payload>.<signature>`. The code is about 150 characters, so it is pasted or loaded from a file, not typed.
  - **The signing key:** the private key never goes into the app, the repo or the database. Signing happens only on the server, in an Edge Function that has the key in its secret environment, and only for a platform admin with two-step login. The offline server contains only the public keys, labelled by `kid`, so the key can be replaced.
  - **Key safety, documented in the README:**
    - **Backup (the user's rules of 2026-10-29):** one password-protected backup file (the password typed hidden by the user), moved to a USB stick and deleted from the PC; the password is kept in Click Group's password manager. Apart from that file and the Edge Function's secret, the key exists nowhere: never on screen, in the repo or git history, in chat, in logs or in CI.
    - **Lost key:** make a new key pair with a new `kid`, and ship its public key in the next release. Licenses signed with the old key keep working, because the old public key stays in the app.
    - **Leaked key:** make a new key pair with a new `kid`, issue every license and activation again with it, and reject the old `kid` in the next release. A server that never installs that release still accepts the old key; that is a limit we accept.
  - **Machine activation:** the offline server shows a machine code, and the seller panel turns license + machine code into an activation code (`GSA1.<payload>.<signature>`) that works only on that PC. The machine code comes from the Windows machine id and the motherboard serial, so reinstalling Windows needs a new activation. Moving to a new PC goes through the seller panel (deactivate the old PC, activate the new one).
  - **Yearly license:** it has an expiry date. After expiry there is a 30-day grace period with a warning, then the gym goes read-only. Renewal is a new signed license code.
  - **Perpetual license with paid updates:** it never expires, but has an "updates until" date. Every release has its build date embedded. The offline server refuses to install a version built after "updates until" and explains why in Kurdish; the installed version keeps working forever. Buying more updates means a new license code with a later "updates until" date.
  - **Warnings:** both license types, and online subscriptions, show in-app warnings in Kurdish to the gym admin 30 days, 7 days and 1 day before expiry or the end of updates.
  - **Seller panel:** it shows each gym's license type, dates and status, and issues renewal codes. Every license issued, activated or revoked is logged there.
  - **Clock tampering:** the offline server records the latest date it has ever seen, from the PC clock and from the newest timestamps in the database. If the PC clock goes back more than 48 hours, it shows a Kurdish warning and treats the license as expired until the clock is corrected. It never trusts the PC clock alone for yearly expiry.
  - **Limits we accept:** a signature stops forged codes, but someone who controls the server PC can patch the program, so the license is a deterrent. An offline PC can't be revoked from a distance: "deactivate" in the seller panel is a record only, and a yearly license still runs out.
  - **How it is built (the MT-5 plan, written by Claude on 2026-10-29 under the working rules; the user asked for everything to be built and tested locally with a throwaway test key, the cloud untouched, and to see the plan for the real key before it is made):** sub-steps **MT-5a** the format in `packages/core` (and the user's receipt wording fix), **MT-5b** database and pgTAP, **MT-5c** signing in the `seller-admin` Edge Function with a local test key, **MT-5d** the seller panel's screens, **MT-5e** the real key's scripts and the README. Not released until the real key exists.
    - **Codes:** `GSL1.<payload>.<signature>` (license) and `GSA1.<payload>.<signature>` (activation). The payload is base64url (no padding) of UTF-8 JSON with short keys; the signature is Ed25519 (WebCrypto, the same code in Deno, Node and Electron) over the ASCII text `GSL1.<payload>` (or `GSA1.…`), so a license can never pass as an activation. With the gym's name, id and code in it a license is about 350 characters, not 150: it is pasted or loaded from a text file, as planned.
    - **License payload:** `v` 1, `lid` license id, `kid`, `gid` gym id, `gc` gym code (the offline server makes its one gym row from it), `gn` the gym's Kurdish name, `t` `yearly` or `perpetual`, `mb` / `md` max branches and devices (null: no limit, as for online gyms), `f` edition features (a list; none are defined yet, so every license has all features and the list is empty), `iat` issue date, and `exp` (yearly) or `upd` (perpetual), all Baghdad calendar dates; a date means the end of that day in Baghdad. Yearly: expiry at most 2 years ahead (an early renewal still fits). Perpetual: "updates until" at most 5 years ahead. Both catch a mistyped year.
    - **Activation payload:** `v`, `aid` activation id, `kid`, `gid`, `mc` machine code, `iat`. **It binds the gym to one PC, not one license**, so a renewal needs only a new license code. A gym has at most one active activation (one server PC); moving deactivates the old one first.
    - **Machine code:** 20 characters shown as `XXXX-XXXX-XXXX-XXXX-XXXX` (Crockford base32: no I, L, O, U): 16 from SHA-256 of the Windows machine id and the motherboard serial, plus 4 check characters, so a typo read over the phone is caught before anything is signed. Typing is forgiving (lowercase, spaces, O for 0, I or L for 1, Kurdish and Arabic digits). Reading the two ids on Windows comes with the offline packaging phase; MT-5 only defines the code.
    - **Keys in the code:** `LICENSE_PUBLIC_KEYS` in `packages/core` (kid → the raw 32-byte public key, base64url) and `REVOKED_LICENSE_KIDS`. Kids are 3–32 of `a-z 0-9 -`. A kid starting with `test-` is a local test key: never in `LICENSE_PUBLIC_KEYS` (a test checks), so no shipped server accepts what it signed.
    - **The signing key:** one Edge Function secret, `LICENSE_SIGNING_KEY`: the private key as a JWK (`kty` OKP, `crv` Ed25519, `d`, `x`, `kid`). The function refuses to sign when the kid is revoked, or is not a `test-` kid and its public half isn't the one in `LICENSE_PUBLIC_KEYS` (a key whose public half hasn't shipped would make codes no server accepts), and it checks every signature it makes before handing out the code. Without the secret, issuing answers `license_key_missing` and everything else works. Locally, `pnpm db:functions` makes a throwaway `test-…` key in `supabase/functions/.env` (git-ignored) when there is none.
    - **Database:** an offline gym's record in the cloud is a bare `gyms` row (`edition` offline, made by `seller_create_offline_gym`): no roles, branch or staff, because those live on its own server PC. The seller can correct its name (the next license carries it); subscription, limits, suspend, lock and support stay online-only. `platform.licenses` and `platform.activations` keep every code with who made it, when, and the revocation or deactivation with its reason (required; both are records only). `platform.license_events` (append-only) logs issued, revoked, activated and deactivated, and `seller_audit_log()` shows it with the other seller actions (a separate table, because widening `platform.audit_logs`' action list needs a drop).
    - **Issuing** follows the create-gym pattern: `seller_prepare_license()` / `seller_prepare_activation()` check everything under the platform admin's session (aal2) before the key is touched and return the gym's name, code and today's Baghdad date; the function signs; `seller_issue_license()` / `seller_issue_activation()` check everything again, decode the code's payload and require it to equal the fields stored, all in one transaction with the event. Postgres can't check an Ed25519 signature, so a platform admin calling the issue function directly could store a code that no server accepts; that is a limit we accept (it grants nothing).
    - **Seller panel:** "new gym" asks for the edition first (an offline gym needs only its code and names). ## 3. Roles & permissions (RBAC)
Do not hardcode role checks in the UI only. Use a permission-based model:
- Tables: `roles`, `permissions`, `role_permissions`, `staff_users` (links to `auth.users`; **one role per staff member**; `all_branches` flag), `staff_branches` (join table — a staff member can be given access to several branches). Everything except the `permissions` catalog belongs to one gym (§2.6)
- Default roles, copied into every gym: **Owner** (خاوەن, every permission, all branches; called Super Admin before the multi-tenant step), **Admin**, **Branch Manager**, **Receptionist**, **Trainer**, **Spa Therapist**, **Accountant**, **Cashier**
- Permissions are granular strings, e.g. `members.create`, `members.delete`, `payments.refund`, `reports.financial.view`, `settings.edit`, `staff.manage`, `lockers.assign`, `discount.apply.max_10`
- Admin can create custom roles and toggle permissions from a matrix UI
- Enforce permissions in **three layers**: RLS policies (via a `has_permission(perm text)` SQL function), server-side validation (guards, Postgres functions), and UI (hide/disable, using the permissions from the last server check)
- Data is scoped by branch: a staff member only sees the branches they have access to — every branch if `all_branches` is true, otherwise the branches listed for them in `staff_branches`. One SQL function, `has_branch_access(branch_id)`, implements this rule for RLS
- Staff features: PIN quick-login for shared reception PCs, session timeout, force password change, deactivate account (never hard delete)

- Duplicate detection on create (same phone / similar name)

- **Decided by the user on 2026-10-19 (Phase 2 plan), built from step 2a:**
  - **Members belong to the whole gym:** everyone with `members.view` sees every member of their gym. The home branch (where the member joined) is a filter.
  - **Member number:** a plain number per gym, shown as `000123` (no prefix), given by the server in order, never changed. Search also finds it as `123`.
  - **Phone:** required, unless the member has no phone of their own (a child); then their emergency contact's phone is required. Iraqi mobiles are typed in any common form and stored as `+9647XXXXXXXXX`; other countries' numbers are allowed with `+` and the country code. Unique per gym, archived members included, so a returning member is restored, not added twice.
  - **Health info** (blood type, medical notes, injuries) is kept apart from the profile. Only `members.medical.view` can read it. Staff with `members.create` may also write it while creating a member, without being able to read it afterwards; later changes need `members.medical.view` and `members.edit`. Staff who can't read it see a "has health notes" badge. The audit log records that health info changed, never the values.
  - **Statuses** staff set: active, suspended, banned, archived. Suspending, banning, archiving and restoring need `members.delete` and a reason (not for restoring). Members are never deleted. Expired and frozen come from the subscriptions (Phase 3) and are never stored on the member.
  - **Duplicates:** the same phone is refused; the same name (as search compares it) or a similar one (the same first two words, or a letter or two apart) is a warning, and the member can still be saved.
  - **In Phase 2:** profile, health info, photos, NFC cards, global search and the Excel/CSV import. Measurements, the waiver with signature and documents come later.

### 4.2 Plans & Subscriptions
- Plans: name, type (time / visit / hybrid / unlimited), duration, visit count, price, gender restriction, allowed hours/days, allowed branches, included services (e.g. 2 free spa sessions, sauna access, locker included), max freeze days, is_active
- Subscribe flow: select plan → start date → discount (respect role limit) → payment (full / partial / installments) → assign/confirm NFC card → print or WhatsApp receipt
- Renew, upgrade/downgrade (pro-rata calculation), **freeze/unfreeze** (extends end date automatically), transfer to another member (with permission), cancel with refund rules
- Plan snapshot stored on each subscription so later price changes don't affect old records
- **Phase 3 plan (written by Claude on 2026-10-24 under the user's working rule: where the spec is silent, the safest sensible default, listed in each release report):**
  - **Plan types** are the four combinations of an end date and a visit count: `time` (a duration, e.g. 1, 3, 6 or 12 months, or a number of days), `visits` (a number of visits, no end date), `hybrid` (both: e.g. 20 visits within 2 months) and `unlimited` (neither: VIP or lifetime). A duration in months ends the day before the same date n months later (1 month from 24 Oct ends 23 Nov), or on that month's last day when it has no such date (from 31 Mar: 30 Apr), so nobody gets less than they paid for; in days it ends n − 1 days after the start.
  - **Prices are in IQD** (whole dinars). A payment may be in USD with that day's rate stored on it; every total and balance is in IQD.
  - **A plan's rules:** gender (anyone, men or women; selling refuses a member of the other gender), the branches it works in (all, or a list), the days of the week and one time window (e.g. mornings only), the most visits per day (empty: no limit; the check-in engine uses 1 for visit plans when empty), and the most freeze days (0: it can't be frozen). Included services (spa sessions, sauna, a locker) come with the Spa and Lockers phases. Plans are never deleted; a plan that isn't sold any more is made inactive. Changing a plan never changes subscriptions already sold (each keeps its own copy of the plan).
  - **Everyone in the gym sees the plans** (they are needed to sell); `plans.manage` adds and edits them.
  - **Selling** is one Postgres function: the subscription, its invoice and item, the first payment and the installments are saved together or not at all. The screen sends the price it showed; if the plan changed meanwhile the sale is refused (`price_changed`) and the screen shows the new price.
  - **Discounts** are a percentage or an amount, limited by the seller's permission (`discount.apply.max_10/25/50/any`, the highest one counts); without one there is no discount. A discount needs a reason.
  - **Debt:** a member's balance is computed (invoices minus payments, never a stored counter). A payment can't be more than what the invoice still owes, so nobody has credit. Installments are due dates with amounts that add up to what was not paid at the sale; payments pay them oldest first, and one past its date and not paid is overdue.
  - **Voids and refunds:** a mistake is voided (`payments.void`, with a reason) only on the day it was made (Baghdad time); later, money goes back as a refund (`payments.refund`, with a reason, at most what was paid). Nothing financial is ever deleted.
  - **Numbers** come from the server per branch, without gaps: invoices `B1-000457`, payment receipts `B1-R000123`.
  - **Who sees money:** invoices and payments need `payments.view` and access to their branch; subscriptions are seen with `members.view`, like members.
  - **Dollars** are whole bills: what they are worth beyond what is owed is change, given back in dinars and kept on the payment (step 3c).
  - **A refund** gives money back and lowers the charge by as much, so it never makes the member owe more (step 3e). **A credit** lowers what an invoice asks for with no money moving: the unused part of a subscription that was changed or cancelled (step 3f).
  - **The unused part** of a subscription is worth its share of what was charged for it: days left of the days sold (frozen days aren't used), visits left of the visits sold, the smaller for hybrid. It first clears what is still owed on its invoice; the rest was paid and not used. Changing the plan takes that rest off the new price (refused when it is worth more than the new plan: cancel with a refund instead); cancelling may give it back. Unlimited plans have nothing to share out, so they can't change plan.
  - **Freezing:** one freeze at a time, from today or later, up to the plan's freeze days in all; the end date moves at once, and back by the days not frozen when it ends early.
  - **Transfers** give what is left (to the same end date, with the freeze days left) to another active member of the gym; the invoice stays with the first member.
  - **The card replacement fee** (spec §1) is an invoice of its own, offered right after a lost or damaged card is replaced.
  - **Receipts** print in the member's language (§0), on an 80mm roll or an A4 page, through the print dialog, which also saves a PDF (browser and Windows app; the Android app has no print dialog yet). WhatsApp receipts come with notifications (Phase 9); silent 80mm printing with the cash register (Phase 8).
  - **A member's membership** (current, frozen, upcoming, expired, none) is computed from their subscriptions and never stored (§4.1); the member list filters by it.

### 6.1 Appearance (ڕووکار)
The app must not have only one look. The default is indigo + light + soft corners. Settings → Appearance has two parts:

1. **Gym appearance** (needs `settings.edit`; stored in the `settings` table as gym-wide rows, so every device of that gym gets it; works the same in both editions; one look for the whole gym, no per-branch override, so saving also needs access to all branches like every gym-wide setting):

If text on the brand color, or the brand color used as text on the page background (light or dark), would fail WCAG AA (4.5:1 for text, 3:1 for icons and borders), it warns before saving. It also warns when a custom color looks like a status color. The presets always pass.
   - **Corner style:** soft / medium / sharp.
   - **Gym logo upload**, shown in the top bar and on receipts (printed in black and white on 80mm printers). PNG, JPEG or WebP only (no SVG). The app resizes it on upload (at most 512 px), and the stored file may be at most 300 KB, checked by the app and again by the database. It is kept in Postgres, not Supabase Storage, so it works in both editions. Without a logo the gym's name is shown.
2. **Personal appearance** (each staff member, saved in their profile and cached on the device for the login and lock screens):
   - Light / dark / follow device (default: follow device).

3. **Status colors are fixed:** green (allowed / paid), amber (warning / expiring) and red (denied / overdue) never follow the brand color.
4. **Everything is built from theme variables:** colors, corners and text size are CSS variables set at runtime, so a change applies instantly without a reload. Other devices pick up a gym change on their next settings refresh (on focus or on a timer).
